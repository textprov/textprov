TextProv

Origin labels that travel with text: human-written, AI-generated, mixed, edited, or unknown. TextProv is an open protocol for keeping those disclosures in the text itself, rather than in a separate file or one application's metadata.

Use it in an editor or content pipeline when you know how text was produced. For example, an AI-writing integration can label the passages it generates for review. TextProv lets cooperating tools preserve and display those labels; it does not enforce honest disclosure.

TextProv provides a shared structure, encoding, and vocabulary for provenance. Applications can exchange the same information and choose how best to use it, from displaying labels to interpreting agent prompts.

Read labels in your browser, add labels with the encoder, or explore use cases. No special font is needed for these tasks.

The labels can travel through copy, paste, and plain-text storage, as long as the receiving software preserves the marks.

A label is a claim about origin, not proof of authorship or a judgment about quality, accuracy, or trustworthiness. TextProv does not detect AI writing or authenticate the source of a claim. Anyone can add, change, or remove marks; unmarked text makes no claim about its origin.

Inspect the marks with utility fonts

The TextProv Utility P9E families are development and debugging adjuncts. They reveal supported marks in a compatible text renderer, without a separate inspection tool. The labels in these samples are already part of the text; JavaScript does not add them.

Applications and sites displaying the content are best placed to decide how to interpret and present provenance. These fonts offer one diagnostic view: Human-labelled text stays plain and AI-labelled text gains a sawtooth. Everyday interfaces can reveal provenance on demand or use it internally.

How does it work?

TextProv's default encoding adds normally invisible Unicode characters called variation selectors after the letters or symbols being labelled. A TextProv reader recognizes these marks and can show their meaning using underlines, colours, or other decorations.

Labels do not identify an author, model, or timestamp; a workflow must store those details separately. An explicit unknown label differs from unmarked text, which has no label.

A code point is a number identifying a character in Unicode. For example, U+0041 identifies A. TextProv uses U+E0101 as the AI label:

U+0041  U+E0101
   A    AI mark

Unicode defines the characters; UTF-8 encodes them as bytes in a file or message. TextProv is not a replacement for UTF-8. A UTF-8 file can store both the letters and their marks; older encodings such as Latin-1 cannot store these marks.

These label meanings are a TextProv convention, not Unicode-registered variation sequences. Software that does not understand TextProv usually shows the ordinary letters. Software that strips invisible characters can remove the labels, so test the path your text takes.

Does TextProv prove a label is true?

No. TextProv standardizes the transport of origin declarations; it does not verify them.

A TextProv workflow has four independent steps:

integration decides → producer marks → transport preserves → consumer interprets

The protocol defines only the middle two: how a producer encodes a state and how a consumer decodes it. It says nothing about how the state was chosen, whether the declaration is honest, or whether the consumer should act on it. A false declaration can be correctly encoded, and a valid decoder can report it without endorsing it.

An advisory protocol can still be useful. robots.txt, canonical links, SPDX license expressions, Semantic Versioning, and RSS all standardize a declaration without proving it is true. Honest participants benefit from a shared vocabulary; adversarial ones cannot be stopped by the format itself. TextProv makes the same trade for origin labels.

If you need cryptographic proof of who produced a file and whether it has been altered, that is a different problem. One answer is C2PA: a signed manifest bound to a file's bytes, shown to readers as Content Credentials. Plain text needs a sidecar file for this — the specification, section 11.4, gives .txt as its example of a format that cannot embed a manifest.

The two approaches survive different things. Select a passage and paste it into a message, and the sidecar, manifest, and signature stay behind with the original file; TextProv labels live in the character sequence itself and travel with the passage. The approaches combine cleanly: mark the text with TextProv, then sign the marked file with C2PA. A copied passage keeps its labels but not the file's signature, so it does not inherit the file's verified status.

TextProv does not create or validate C2PA manifests, and its labels are not Content Credentials. Neither an origin label nor a valid signature says anything about whether the text is factually correct.

Use cases

TextProv can carry passage-level origin labels through workflows where text moves between files, tools, and people.

Writers tracking drafts

Bloggers, journalists, and other writers can distinguish their own prose from AI-generated passages while drafting. The labels remain attached when compatible tools preserve the Unicode marks.

Developers reviewing AI-assisted code

Developers can mark generated code and comments so collaborators know which passages may need extra review, testing, or explanation.

Auditing content

Auditors, editors, and compliance reviewers can inspect labelled passages in place, without relying on a particular document format or a separate metadata file.

Publishing and collaboration tools

Applications can retain origin labels when accepting, storing, displaying, and exporting text. Implementations are available for Python, JavaScript, and Ruby.

Agent prompt integrations

A prompt can combine an operator's instructions with text copied from model output. TextProv marks can preserve that distinction, giving an agent integration context that would otherwise be lost. An integration could use the decoded states to experiment with how much weight to give each passage. This requires further integration; TextProv provides the common foundation, and applications choose their policies. Treating unmarked input as operator-written depends on the workflow. See the application use discussion.

A TextProv label records a claim about a passage's origin. It does not prove authorship, accuracy, or whether the passage was later edited.

Try a utility font

  1. Download and unzip one family or the complete set.
  2. Install its .ttf file.
  3. Select the “TextProv … Utility P9E” family in your editor. Older family menus may list the Proportional family as “TextProv Propo Utility P9E”.
  4. Open the marked text sample. Reload this page to check the local-font example.

Font rendering varies across applications. These utility fonts include selector mappings and a glyph-substitution fallback; if labels do not appear, inspect the text with the browser reader. See the utility font guide for build instructions and tested rendering paths.

What is included and supported?

Each family ZIP includes an installable TTF, a WOFF2 webfont, its upstream OFL licence, and a README with attribution and source details. The combined ZIP contains all five families and their notices.

These are regular-weight Latin subsets with common punctuation, not full replacements for the original fonts. Human and AI states are supported; the browser reader can display other TextProv states. Fixed and Mono have the same spacing classification but distinct designs; Sans, Serif, and Proportional have variable-width text.

Keep selector-encoded text for sharing. Glyph decoration is a debugging view, and its sawtooth style does not define how an application should display provenance.

Sources, licences, and reproducible builds

The utility set derives from Source Sans 3, Source Serif 4, IBM Plex Mono, Source Code Pro, and Atkinson Hyperlegible. Each modified font remains licensed under SIL OFL 1.1; the build code is MIT licensed. Original copyright and licence notices are retained, and the fonts receive their own TextProv family names.

The build manifest records pinned source revisions and input/output checksums. The utility build notes describe the scope, source licences, and reproducible build command.

Implement the protocol

The protocol is Draft 0.1 and may change incompatibly. Start with the specification for its maturity, label meanings, and encoding rules; the code-point registry for the assigned marks; and the conformance fixtures to check your implementation.
