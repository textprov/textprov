TextProv

Origin labels that travel with text: human-written, AI-generated, mixed, edited, or unknown. TextProv is an open protocol for keeping those disclosures in the text itself, rather than in a separate file or one application's metadata.

Use it in an editor or content pipeline when you know how text was produced. For example, an AI-writing integration can label the passages it generates for review. TextProv lets cooperating tools preserve and display those labels; it does not enforce honest disclosure.

Read labels in your browser, add labels with the encoder, or integrate a package. No special font is needed for these tasks.

The labels can travel through copy, paste, and plain-text storage, as long as the receiving software preserves the marks.

A label is a claim about origin, not proof of authorship or a judgment about quality, accuracy, or trustworthiness. TextProv does not detect AI writing or authenticate the source of a claim. Anyone can add, change, or remove marks; unmarked text makes no claim about its origin.

What travels with the text?

TextProv's default encoding adds normally invisible Unicode characters called variation selectors after the letters or symbols being labelled. A TextProv reader recognizes these marks and can show their meaning using underlines, colours, or other decorations.

Labels do not identify an author, model, or timestamp; a workflow must store those details separately. An explicit unknown label differs from unmarked text, which has no label.

A code point is a number identifying a character in Unicode. For example, U+0041 identifies A. TextProv uses U+E0101 as the AI label:

U+0041  U+E0101
   A    AI mark

Unicode defines the characters; UTF-8 encodes them as bytes in a file or message. TextProv is not a replacement for UTF-8. A UTF-8 file can store both the letters and their marks; older encodings such as Latin-1 cannot store these marks.

These label meanings are a TextProv convention, not Unicode-registered variation sequences. Software that does not understand TextProv usually shows the ordinary letters. Software that strips invisible characters can remove the labels, so test the path your text takes.

Alongside C2PA and sidecar metadata

TextProv focuses on plain text and passages copied between applications. It complements C2PA (Content Credentials), rather than replacing its signed provenance records. TextProv is not a provenance format for images, audio, or video.

C2PA binds provenance records to digital assets using cryptographic hashes and signatures. These records are packaged in manifests, which can be embedded in supported formats or stored externally. A sidecar is a separate file holding metadata for an asset. C2PA does not exclude plain text: its technical specification, section 11.4, explicitly names .txt files as a reason to use an external manifest.

The distinction is what accompanies a copied passage. Copying only text into another editor or message does not automatically carry a sidecar file, a document's embedded manifest, or its verification context. TextProv puts origin labels in the character sequence, so a passage can retain its labels when copied without that surrounding metadata, provided the receiving software preserves the marks.

A workflow could use both: TextProv for labels within the text, and C2PA for a signed record bound to the marked file. Adding or removing marks changes the text's bytes, so that step belongs before creating a manifest that binds those bytes. A copied passage does not inherit the original file's verified status merely because its TextProv labels remain.

TextProv does not create or validate C2PA manifests, and its labels are not Content Credentials. Coexistence is a workflow choice, not a built-in integration. Neither an origin label nor a valid signature establishes that the text is factually correct.

Use TextProv in your application

Python: mark a file and read it back

Requires Python 3.9+. Run these commands in a terminal on macOS or Linux, in a directory where you can create files. They overwrite draft.txt and marked.txt if those files already exist. They create an isolated environment, install TextProv from PyPI, and write a marked UTF-8 file.

python3 -m venv .venv
.venv/bin/python -m pip install textprov
printf 'Hello from TextProv.\n' > draft.txt
.venv/bin/python -m textprov -o marked.txt mark --ai draft.txt
.venv/bin/python -m textprov inspect marked.txt

The report identifies AI-marked text even if your editor shows no decoration. Open marked.txt and paste its contents into the reader above to see the label.

Run .venv/bin/python to open a Python prompt in that environment, then try the API. Marking and rendering are separate operations; the HTML output needs CSS to make the label visible:

import textprov

marked = textprov.mark("Hello", state="ai")
print(textprov.to_html(marked))
print(textprov.strip_marks(marked))  # Hello

JavaScript: display existing marks

The npm package reads marks; it does not add them. Install it in your web project:

npm install textprov

With a bundler that supports CSS imports, render a container after adding its text:

import textprov from "textprov";
import "textprov/textprov.css";

const preview = document.createElement("p");
preview.textContent = "A\u{E0101}"; // A followed by the AI mark
document.body.append(preview);
textprov.render(preview);

The result is an AI-labelled A, styled without a special font. The reader wraps marked text in HTML spans with a data-prov attribute. The bundled CSS is optional; applications can choose their own presentation.

Ruby: mark, read, and render

The Ruby implementation can add marks, read them, and render HTML, and includes a command-line interface. Requires Ruby 3.2+ and Git for this source-based example. From the repository root, run only the last command; otherwise, clone the repository first:

git clone https://github.com/textprov/textprov.git
cd textprov
ruby -I ruby/lib -r textprov -e 'puts Textprov.to_html(Textprov.mark("Hello", state: "ai"))'

This prints HTML containing an AI-labelled span. Ruby API and CLI reference →

The source fonts' older third selector has a different meaning from TextProv v1, so it is deliberately excluded from these subsets. See the font build notes and attribution or the font and interchange guide.

Font display depends on the application's text-rendering engine. The project's tests found that HarfBuzz displayed the selector variants while macOS CoreText did not. Keep selector-encoded text for sharing; the guide's private-use (PUA) samples require a matching font and are for controlled local experiments.

Implement the protocol

The project is early-stage; version 1 of the protocol is treated as stable. Start with the specification for label meanings and encoding rules, the code-point registry for the assigned marks, and the conformance fixtures to check your implementation.
